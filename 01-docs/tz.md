# PostCup — Технічне завдання
## Детальний опис екранів, логіки та бази даних

**Формат кав'ярні:** тільки на винос (без столиків)
**Точки продажу:** одна точка, кілька касирів по змінах
**Облік складу:** точний, по рецептурах (списання інгредієнтів)

## 1. Ролі користувачів
- Власник (Admin): повний доступ — меню, склад, звіти, працівники, налаштування
- Касир (Cashier): тільки каса — створення замовлень, перегляд своєї зміни

## 2. Екрани системи

### 2.1. Екран входу
Логін/PIN для касира. Логін+пароль для власника.

### 2.2. Екран каси
Ліва частина — меню: вкладки "Напої"/"Десерти", підкатегорії, картки товару з ціною, модифікатори (розмір, тип молока).
Права частина — кошик: список позицій, кількість, сума, кнопки оплати "Готівка"/"Картка".
Після оплати: фіскалізація через Checkbox/Vchasno API → друк чеку на термопринтер → списання інгредієнтів зі складу.

### 2.3. Екран "Зміна"
Почати зміну (ввід готівки на старті), закрити зміну (підсумок продажів готівка/картка), історія замовлень за зміну.

### 2.4. Екран меню (Admin)
Додати/редагувати/видалити товар: назва, категорія, ціна, рецептура (список інгредієнтів+кількість), модифікатори розмірів.

### 2.5. Екран складу (Admin)
Список інгредієнтів (назва, одиниця виміру, залишок), ручне поповнення, історія списань, сповіщення про низький залишок.

### 2.6. Екран звітів (Admin)
Виручка за день/тиждень/місяць, розбивка готівка/картка, топ-товари, звіт по змінах касирів.

### 2.7. Екран працівників (Admin)
Список касирів, додавання нового (ім'я+PIN), статистика по касиру.

## 3. Логіка списання складу
Кожен товар має рецептуру (інгредієнт + кількість на порцію). При продажі система множить кількість на кількість проданих порцій і віднімає від залишку. Якщо залишок йде в мінус — продаж все одно дозволяється, але власнику показується попередження.
Приклад: Капучино M = 7г кава + 200мл молоко. Продано 3 шт → списується 21г кави + 600мл молока.

## 4. Логіка змін
Касир входить по PIN. При першому продажі за день система питає "Почати нову зміну?". Всі замовлення прив'язуються до касира і зміни. При закритті зміни фіксується підсумок для звірки готівки.

## 5. Структура бази даних

users: id, name, pin_code, role (admin/cashier), created_at
categories: id, name, parent_category_id
products: id, name, category_id, price, is_active
product_modifiers: id, product_id, name, price_delta
ingredients: id, name, unit, current_stock
product_recipe: id, product_id, ingredient_id, quantity_per_unit
shifts: id, cashier_id, opened_at, closed_at, opening_cash, closing_cash, total_sales
orders: id, shift_id, cashier_id, total_amount, payment_method, fiscal_receipt_id, created_at
order_items: id, order_id, product_id, modifier_id, quantity, price_at_sale
stock_movements: id, ingredient_id, change_amount, reason, order_id, created_at

## 7. Прийняті рішення
- Друк чеків: потрібен фізичний термопринтер, підключення через ESC/POS стандарт
- Оплата карткою: окремий банківський POS-термінал без інтеграції, кнопка в системі лише позначає спосіб оплати для звітності

## 8. Відкриті питання
